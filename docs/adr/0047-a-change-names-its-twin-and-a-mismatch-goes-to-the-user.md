# A Change names its Twin, and a Twin mismatch goes to the user

vercel-labs/ui asks every agent to open the file that already does the same job before writing a line, and to copy its shape. Its rule for the hard case is one sentence: "If two twins disagree, the shape is wrong in one of them. Say so instead of picking one." KDDESIGN's loop had neither half. `/design-delta` recorded what a Change looks like and why, never what in the project it should have been built from, and the design rules named looks and placements, never files. So a second Select with its own markup shipped as an ordinary Fix, and the next agent that needed a select found two and picked one at random.

So the loop now carries Twins:

- **`/design-delta` names a Twin for each Change that adds or reworks a control or a component**: the piece of the project, at the After, that already does that job. The Delta's `Twin:` line says whether the Change follows it (renders it, or copies its markup and values) or differs, and how: the markup, and each look value both ways. When the job already has two pieces that differ from each other, that is said on the same line. The run never picks a winner and never sweeps the repo: only jobs the Change's own elements do.
- **A mismatch proposes a rule candidate**, `rule/twin-<job>`, whose sentence names the piece more files use (ties: the older file), with the commit that brought the mismatch as its source. The count is a fact read from the code, not a reason, so the draft's Why stays `—` unless a source states one.
- **One mismatch is enough evidence.** Other candidates need two sources because one remark may be chance. A mismatch is not chance: the two pieces exist, and the only open question is which one stays, which only the user can answer. So a `twin` source clears the bar alone, as a stated one does. After a Reject it does not: coming back needs two new sources, or every later mismatch on that job would ask again.
- **`/design-lessons` lists the Twins** on the item, each with how many files use it and what differs, the recommended one first. Accept writes the drafted Rule with a `Twin:` field; a Note that names another listed piece makes that one the Twin. The Verdicts format does not change, so the Nudge's Approve and its one-by-one Verdicts work as before.
- **A Rule with a `Twin:` field is followed and checked like any Rule.** Agents read it through the pointer line, which now says to build each job from the Twin its Rule names; `/crazy-prototype` builds its mocks from it in a project; `/design-delta` writes a `Breaks:` line for a Change that does the job without it.

Not chosen: a script that finds Twins. ui's `expert-scope.mjs` works because one repo's folder layout is fixed; KDDESIGN runs in any project, and what counts as "the same job" (a Select, a Dropdown, a Picker) is a judgment a script would get wrong both ways. Not a new group on the Design Lessons Review either: a Twin item is a candidate like any other, decided with the same three Verdicts. And not `/design-whip` or `/design-morph`, which stand outside the loop; whip's rule 2 already asks for reuse inside one change, and nothing it decides is recorded.
