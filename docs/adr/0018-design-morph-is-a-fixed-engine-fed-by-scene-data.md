# design-morph is a fixed engine fed by scene data

The first film (Meme Maker, three acts) was written by hand: a 350-line engine, a player, and 400 lines of scene code per product, with the stage size of 1440 × 900 written into fifteen places across the engine, the player, the page CSS and the capture scripts. Every film written that way repeats the engine's bugs and fixes them again: the clamped clock, the round clip layers, the exit drift. So `/design-morph` follows ADR 0006: the engine, player, build, checker and frame tools ship in `skills/design-morph/` and a run never edits them. A run writes `scene.json` and one `acts/<key>.json` per act, plain data with every product value in it: the stage size and gutter (a config value, so a portrait phone stage works the same as a desktop one), the accent, fonts and motion tokens, the old-skin colors, and each element's old and new state. Because the state math has no DOM, `check.mjs` runs the engine itself in Node and sees exactly what the page will draw.

A product will need something the fields do not cover (the first film had a split before/after image and a three-way segmented control). That goes through one extension point: a `scene.css` whose selectors must name an `x-` class and are scoped under the stage, and `types/<name>.js` that register an element type with `Morph.type()`, drawing inside a box the engine still owns, so the checker covers it. Not chosen: letting a run patch the engine for its film, which is how the first film's fixes ended up unshared; and a JS scene format, which reads well but cannot be read back, diffed or checked without running the run's code.
